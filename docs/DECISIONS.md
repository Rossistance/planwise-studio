## RFI / Submittal pipeline (the big v3 feature)

Outbound:
1. PM creates an RFI or Submittal in-app, attaching drawings/uploads from the Drawings register.
2. AI drafts the RFI/Submittal **document** using context from the attached drawings and their annotations.
3. AI drafts the **email** (recipient = customer or sub), attaches the document, and creates a **draft in the user's logged-in desktop Outlook Drafts folder** — the PM reviews and hits Send in Outlook. The app never sends mail itself.

Inbound:
4. App polls the desktop Outlook inbox X times/day (plus a manual Refresh button), matching replies to that exact sent thread (COM `ConversationID`).
5. Intent/sentiment analysis on the reply: for RFIs, extract the answer from the email body onto the RFI record; for Submittals, capture the disposition (Approved / Approved as Noted / Revise & Resubmit / Rejected).
6. Returned attachments (annotated markups) are captured back onto the same record/thread as a new revision linked to the original.

Technical basis: desktop Outlook via COM (pywin32) exactly as SiteScope's
`outlook_desktop.py` already does — no Graph, no admin approval, no stored
credentials. Draft creation, attachment, and ConversationID reply-matching are
the same COM surface, verified available 2026-08-08.

Working assumption (flag if wrong): AI-extracted answers/dispositions are
**staged for one-click PM confirmation**, not silently applied — consistent
with the app's provenance ethos. The email body and returned files are kept as
evidence on the record either way.

### Drawings workspace + annotation layer model

The Drawings page becomes a **workspace**: in-app PDF viewer with a markup
tool. One document library feeds everything — the RFI and Submittal pages pick
from the same uploaded sets.

The internal-markup isolation requirement dictates the storage model:

- **The original PDF is immutable.** Annotations are NEVER burned into the
  file. Each annotation is a vector overlay record — document, page, shapes,
  author, timestamp — belonging to a named **layer**.
- **Layer contexts:**
  - `internal` — redlines / site markups by the White Electrical / AXIS
    teams, made on the Drawings page. Persistent, carry state everywhere the
    document appears in the app.
  - `rfi:<id>` / `submittal:<id>` — markups made while working a specific
    RFI/Submittal (browse the set, land on a page, mark it up, attach).
- **Compositing rules:**
  - In-app viewing: original + whichever layers the context calls for
    (internal layers visible to the team everywhere).
  - **Outbound extract: original page + ONLY that RFI/Submittal's layer.**
    Internal layers are excluded by construction — a customer can never see
    a WECC/AXIS redline because the render path never composites it.
- **Single-page extract:** attaching a page to an RFI/Submittal extracts that
  page (plus its outbound layer) into the document sent; the drawing package
  itself is never modified.
